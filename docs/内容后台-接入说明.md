# 内容层接入说明（Decap CMS + Markdown）

> 目标：不再改 `index.html` 里的 `WORKS`，写稿只产出 Markdown；前台照旧用 `#/works/*`、`#/archive/*` 路由。

## 一、现在的内容链路

```
admin/（Decap CMS 后台）
   └─ 提交 Markdown → content/{long,short,series}/*.md
                         │
                node scripts/build-content.mjs        ← GitHub Actions 自动执行
                         │
                  content-index.json（构建产物，已提交）
                         │
             Cloudflare Pages 自动部署
                         │
   index.html 启动时 fetch content-index.json → WORKS / publishedWorks
                         └─ 失败则回退 index.html 内的 STATIC_WORKS（离线也看得见）
```

数据来源优先级：**content-index.json（Markdown）→ /api/works（D1，若已绑定）→ STATIC_WORKS**。
路由、分区筛选、排序比较函数、搜索、每日精选、随机漫游、主题、写信、字号记忆全部未改。

## 二、作者怎么发文

### 方式 A：线上后台（Decap CMS）
1. 打开 `https://<你的站点>/admin/`
2. 选「长篇 / 短篇 / 系列日志」→ 新建
3. 填 title、slug（小写字母+短横线）、系列、日期、封面图、标签、摘要（可空）、正文
4. Publish → Decap 直接提交到 `main`
5. Actions 生成 `content-index.json` → Pages 重新部署（约 1~2 分钟）

> **前提：需要 GitHub OAuth 中转**。Decap 是纯前端 CMS，自己无法完成 GitHub OAuth。
> 二选一：
> - 部署一个 OAuth Worker（如 `decap-proxy` / `sveltia-cms-auth`），把 `admin/config.yml` 里的
>   `base_url` 换成它的地址；再在 GitHub 建一个 OAuth App，回调填 `<worker>/callback`。
> - 或用 Cloudflare Access / 自建 Worker 做反代，把后台限制在你自己登录后可见。
>
> 当前 `config.yml` 里是占位地址 `https://wcrow-cms-oauth.example.workers.dev`，**未替换前后台登录会失败**。

### 方式 B：本地写稿（不需要任何 OAuth）
```bash
cd wcrow
npx decap-server            # 起本地代理 http://localhost:8081
python3 -m http.server 8791 # 另开一个终端起静态服务
# 浏览器打开 http://localhost:8791/admin/
```
`config.yml` 已开启 `local_backend: true`，此时保存会直接写本地文件，之后正常 `git commit && git push`。

### 方式 C：直接改 Markdown（最稳）
把 `.md` 放进 `content/long|short|series/`，frontmatter 参考任一现有文件，然后：
```bash
node scripts/build-content.mjs   # 本地重建索引
git add content content-index.json && git commit && git push
```
（即使忘了跑，Actions 也会在 push 后自动补生成。）

## 三、字段约定

| frontmatter | 说明 |
|---|---|
| `title` | 作品名，前台自动加《》 |
| `slug` | 路由标识，必须唯一；`#/works/<slug>` |
| `type` | `series` / `novel-long` / `novel-short` / `essay`；决定归档分区归属（建议只在需要跨目录归档时手改） |
| `series` | 所属系列名（可选），如《兰州美食图鉴》 |
| `orderInSeries` | 系列内序号（可选），同系列内按此升序 |
| `date` | `YYYY-MM-DD`；脚本会把时间戳归一成日期 |
| `status` | `published` / `draft`；draft 不会出现在前台 |
| `coverImage` | 作品自身插图；留空则前台用统一备用图 |
| `tags` | 标签数组，参与检索 |
| `excerpt` | 摘要（可选）；留空则首页从正文只读截取 100~120 字 |
| `relatedSlugs` | 相关作品 slug 数组（可选） |
| 正文 | frontmatter 之后的全部内容，原样保留，支持 `![说明](url)`、`[image: url \| 说明]` |

## 四、为什么不直接用「Pages 构建时读 Markdown」

Cloudflare Pages 目前通过仓库里的 `index.html` 直接托管（无构建步骤）。两种等价做法：

1. **（已落地）GitHub Actions 生成 JSON 并提交** —— 不依赖 Pages 配置，改完即生效。
2. 若你在 Pages 里加了构建命令，可改成 `node scripts/build-content.mjs` + 输出目录 `/`，
   这样就不需要把那 80KB 的 JSON 提交进仓库（Actions 也可删掉）。

## 五、自动化落地：GitHub Actions 需要 `workflow` scope

仓库里已经写好 `.github/workflows/content-index.yml`（content/ 变更 → 重建索引 → 提交）。
但**用 GitHub API 创建/修改 workflow 文件需要 token 带 `workflow` 权限**，本次推送使用的
token 没有该权限，所以远端暂时缺少这个文件。二选一即可补上：

**A. 网页手工放一次（约 1 分钟）**
仓库根目录 → `Add file` → `Create new file` → 文件名填
`.github/workflows/content-index.yml` → 把
`docs/参考-GitHub-Actions/content-index.yml` 的内容整段粘进去 → Commit。
之后每次改 `content/` 都会自动重建索引。

**B. 换成 Pages 构建命令（不需要 Actions）**
Cloudflare Pages → 项目设置 → Build command 填
`node scripts/build-content.mjs`，Build output directory 填 `/`。
这样每次部署都会现算索引；`content-index.json` 也就可以不再进仓库。

> 没有这两者时，站点仍可正常工作：本地改完 Markdown 跑一次
> `node scripts/build-content.mjs` 再提交即可（前台读的是仓库里的 content-index.json）。

## 五、替代方案：D1 数据库 + Pages Functions（何时该换）

本仓库已经内置 `functions/api/works.js`（D1 CRUD）与 `functions/api/letters.js`，前台也保留了 `/api/works` 的合并逻辑。如果你的需求变成下面任意一条，建议改走 D1：

- 需要**秒级发布**（不想要「提交 → Actions → 部署」这一两分钟）
- 需要**定时发布 / 草稿预览 / 版本回滚**
- 需要**多个作者协作、按人分权限**
- 内容量大到 JSON 索引体积失控（目前 7 篇 81KB，约 100 篇时会到 1MB 级）

### 改动范围（D1 路线）
| 位置 | 改动 |
|---|---|
| `wrangler.toml` / Pages 设置 | 绑定 D1 数据库到变量 `DB` |
| `functions/api/works.js` | 已实现增删改查，直接可用（表结构见文件顶部注释） |
| `functions/api/admin/*`（新增） | 写操作鉴权（Bearer token），现在只有 CORS 没有鉴权 |
| 后台 | 现有 `/admin/` 换成极简写稿页（调 `/api/works`），或继续用 Decap + 同步脚本 |
| 前台 `index.html` | 无需改：`syncWorksFromBackend()` 已经会拉 `/api/works` 并合并覆盖 |
| `content/` | 可保留为「冷备份」，或迁移完成后删除 |

### 实施步骤（D1 路线）
1. `wrangler d1 create wcrow`，在 Pages 项目里绑定 `DB`
2. 执行建表 SQL（`functions/api/works.js` 顶部注释里已给出）
3. 用一次性脚本把 `content/*.md` 导入 D1（可按现成的 works 字段映射）
4. 给写接口加鉴权（否则任何人都能改库），再在后台调用
5. 访问 `/api/works` 验证返回，前台会自动优先使用它
6. 删除 `content-index.json` 与 Actions（或保留双轨，前台优先级已定）

> 取舍：D1 换来即时发布与协作，但失去「内容即文件」的 Git 版本历史与零运维特性；
> 对**单人长期写作**的站点，Markdown + 自动索引已经是够用且更省心的方案。
