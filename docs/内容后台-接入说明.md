# 内容层接入说明（Decap CMS + Markdown）

> 目标：不再改 `index.html` 里的 `WORKS`，写稿只产出 Markdown；前台照旧用 `#/works/*`、`#/archive/*` 路由。

## 一、现在的内容链路

```
admin/（Decap CMS 后台）
   └─ 提交 Markdown → content/{long,short,series}/*.md
                         │
                node scripts/build-content.mjs        ← Cloudflare Pages 构建命令（或 GitHub Actions）
                         │
                  content-index.json（构建产物，可提交也可现算）
                         │
             Cloudflare Pages 自动部署（每次 push 到 main 都会触发）
                         │
   index.html 启动时 fetch content-index.json → WORKS / publishedWorks
                         └─ 失败则回退 index.html 内的 STATIC_WORKS（离线也看得见）
```

数据来源优先级：**content-index.json（Markdown）→ /api/works（D1，若已绑定）→ STATIC_WORKS**。
索引输出是**确定性的**（只含 `source / count / fingerprint / works`，不含时间戳），
所以"内容没变"时重新构建不会产生 diff，Actions / Pages 不会无意义重复提交。
路由、分区筛选、排序比较函数、搜索、每日精选、随机漫游、主题、写信、字号记忆全部未改。

## 二、作者怎么发文

### 方式 A：线上后台（Decap CMS）
1. 打开 `https://<你的站点>/admin/`
2. 选「长篇 / 短篇 / 系列日志」→ 新建
3. 填 title、slug（小写字母+短横线）、系列、日期、封面图、标签、摘要（可空）、正文
4. Publish → Decap 直接提交到 `main`
5. Actions 生成 `content-index.json` → Pages 重新部署（约 1~2 分钟）

> **前提：需要 GitHub OAuth 中转**。Decap 是纯前端 CMS，自己无法完成 GitHub OAuth。
> 二选一：
> - 部署一个 OAuth Worker（如 `decap-proxy` / `sveltia-cms-auth`），把 `admin/config.yml` 里的
>   `base_url` 换成它的地址；再在 GitHub 建一个 OAuth App，回调填 `<worker>/callback`。
> - 或用 Cloudflare Access / 自建 Worker 做反代，把后台限制在你自己登录后可见。
>
> 当前 `config.yml` 里是占位地址 `https://wcrow-cms-oauth.example.workers.dev`，**未替换前后台登录会失败**。

### 方式 B：本地写稿（不需要任何 OAuth）
```bash
cd wcrow
npx decap-server            # 起本地代理 http://localhost:8081
python3 -m http.server 8791 # 另开一个终端起静态服务
# 浏览器打开 http://localhost:8791/admin/
```
`config.yml` 已开启 `local_backend: true`，此时保存会直接写本地文件，之后正常 `git commit && git push`。

### 方式 C：直接改 Markdown（最稳）
把 `.md` 放进 `content/long|short|series/`，frontmatter 参考任一现有文件，然后：
```bash
node scripts/build-content.mjs   # 本地重建索引
git add content content-index.json && git commit && git push
```
（即使忘了跑，Actions 也会在 push 后自动补生成。）

## 三、推荐路线：把 GitHub 网页当后台（零折腾）

不需要 OAuth、不需要后台，只要把 GitHub 的网页编辑器当写作界面：

1. 打开 `https://github.com/kenjcha-wq/wcrow/tree/main/content/series`（或 `long` / `short`）
2. 右上角 **Add file → Create new file**
3. 文件名写 `<slug>.md`（例如 `lamian.md`，只用小写字母、数字、短横线）
4. 粘贴下面的模板，改内容后 **Commit changes**
5. Cloudflare Pages 检测到 `main` 有新提交 → 自动构建 → 1~2 分钟后上线

### 标准 Frontmatter 模板（可直接复制）

```markdown
---
title: "新作品标题"
slug: "new-work"
date: "2026-11-04"
series: "兰州美食图鉴"
type: "series"
coverImage: "https://images.unsplash.com/photo-1547592180-85f173990554?auto=format&fit=crop&w=1200&q=85"
tags: ["兰州", "随笔"]
excerpt: "这是摘要"
---

正文从这里开始，段落之间空一行。

第二段。插图可以写 ![说明](图片地址)，或单独一行 [image: 图片地址 | 说明]。
```

字段说明（这份模板已实测可被 `scripts/build-content.mjs` 完整解析）：

| 字段 | 必填 | 说明 |
|---|---|---|
| `title` | ✅ | 作品名，前台自动加书名号；**不要**自己写《》 |
| `slug` | ✅ | 路由标识 `#/works/<slug>`；必须唯一，改它等于换网址 |
| `date` | ✅ | `YYYY-MM-DD`（写成 `2026-11-04T10:00:00Z` 也会被归一成日期） |
| `type` | 建议 | `series` / `novel-long` / `novel-short` / `essay`，决定归档分区 |
| `series` | 可选 | 所属系列，如 `兰州美食图鉴` |
| `orderInSeries` | 可选 | 同系列内的排序序号（数字） |
| `coverImage` | 可选 | 作品自身插图；留空则用统一备用图 |
| `tags` | 可选 | `["兰州", "随笔"]` 或 `兰州, 随笔` **两种写法都支持** |
| `excerpt` | 可选 | 首页摘要；留空则自动从正文截取 100~120 字 |
| `relatedSlugs` | 可选 | 相关作品 slug 数组；写错/不存在的会被**静默忽略**，不报错 |
| `status` | 可选 | `published`（默认）/ `draft`；**draft 不会出现在首页、归档、检索，直链也打不开** |
| 正文 | ✅ | `---` 之后的部分，原样保留（含标点、空行、图片语法） |

> 写成草稿：把 `status` 设为 `"draft"`，前台三处（首页、归档、检索）会自动过滤，
> 连 `#/works/<slug>` 直链也会提示"未找到该篇作品"；改回 `"published"` 即发布。

## 四、Cloudflare Pages 自动构建（替代 GitHub Actions）

> 说明：因为给 DSH 的 token 没有 `workflow` 权限，`.github/workflows/content-index.yml`
> 没能推到远端（内容备份在 `docs/参考-GitHub-Actions/content-index.yml`）。
> 直接用 Pages 构建命令更省事，也不需要任何额外权限。

### 一次性配置（Cloudflare 控制台）
1. Cloudflare Dashboard → **Workers & Pages** → 选中本站的 Pages 项目 → **Settings**
2. **Build configuration → Edit**
3. 按下表填写：

| 配置项 | 填什么 |
|---|---|
| Framework preset | `None` |
| Build command | `node scripts/build-content.mjs` |
| Build output directory | `/` |
| Root directory | 留空（仓库根） |

4. **Environment variables（可选）**：加 `NODE_VERSION = 20`，避免默认 Node 版本过低
5. 保存 → **Deployments → Retry deployment** 立即验证一次

### 之后每次发文会发生什么
```
GitHub 网页改 content/…md  →  commit 到 main
        →  Cloudflare Pages 自动触发构建
        →  node scripts/build-content.mjs 生成最新 content-index.json
        →  发布（约 1~2 分钟）
```
- 每次 push 到 `main` 都会重建，所以**改了 Markdown 就等于发布**，不需要你本地跑脚本。
- 构建命令失败时 Pages 不会发布坏版本，旧版本继续在线（构建日志里能看到具体是哪个 `.md` 的 frontmatter 有问题）。
- 构建脚本的校验：缺 `title`/`slug`、`slug` 重复、`content/` 为空 → 直接报错并列出文件名，避免发出错版。
- 如果你**不想**配置构建命令：仓库里的 `content-index.json` 也可用，但需要你本地跑一次
  `node scripts/build-content.mjs` 再提交，否则前台看到的还是旧索引。

### 与 GitHub Actions 的关系（二选一，不要同时开）
- 只用 Pages 构建：`.github/workflows` 里保持空着即可（当前远端就是空的）。
- 想用 Actions：把 `docs/参考-GitHub-Actions/content-index.yml` 复制到
  `.github/workflows/content-index.yml` 并在 GitHub 网页提交即可（需要 token 有 `workflow` 权限）。

## 五、字段约定

| frontmatter | 说明 |
|---|---|
| `title` | 作品名，前台自动加《》 |
| `slug` | 路由标识，必须唯一；`#/works/<slug>` |
| `type` | `series` / `novel-long` / `novel-short` / `essay`；决定归档分区归属（建议只在需要跨目录归档时手改） |
| `series` | 所属系列名（可选），如《兰州美食图鉴》 |
| `orderInSeries` | 系列内序号（可选），同系列内按此升序 |
| `date` | `YYYY-MM-DD`；脚本会把时间戳归一成日期 |
| `status` | `published` / `draft`；draft 不出现在首页/归档/检索，直链也打不开 |
| `coverImage` | 作品自身插图；留空则前台用统一备用图 |
| `tags` | 标签，参与检索；数组（`["a","b"]`）或逗号分隔字符串（`a, b` / `a，b`）都支持 |
| `excerpt` | 摘要（可选）；留空则首页从正文只读截取 100~120 字 |
| `relatedSlugs` | 相关作品 slug 数组（可选）；找不到的 slug 会被静默忽略，不会报错 |
| 正文 | frontmatter 之后的全部内容，原样保留，支持 `![说明](url)`、`[image: url \| 说明]` |

## 六、替代方案：D1 数据库 + Pages Functions（何时该换）

本仓库已经内置 `functions/api/works.js`（D1 CRUD）与 `functions/api/letters.js`，前台也保留了 `/api/works` 的合并逻辑。如果你的需求变成下面任意一条，建议改走 D1：

- 需要**秒级发布**（不想要「提交 → Actions → 部署」这一两分钟）
- 需要**定时发布 / 草稿预览 / 版本回滚**
- 需要**多个作者协作、按人分权限**
- 内容量大到 JSON 索引体积失控（目前 7 篇 81KB，约 100 篇时会到 1MB 级）

### 改动范围（D1 路线）
| 位置 | 改动 |
|---|---|
| `wrangler.toml` / Pages 设置 | 绑定 D1 数据库到变量 `DB` |
| `functions/api/works.js` | 已实现增删改查，直接可用（表结构见文件顶部注释） |
| `functions/api/admin/*`（新增） | 写操作鉴权（Bearer token），现在只有 CORS 没有鉴权 |
| 后台 | 现有 `/admin/` 换成极简写稿页（调 `/api/works`），或继续用 Decap + 同步脚本 |
| 前台 `index.html` | 无需改：`syncWorksFromBackend()` 已经会拉 `/api/works` 并合并覆盖 |
| `content/` | 可保留为「冷备份」，或迁移完成后删除 |

### 实施步骤（D1 路线）
1. `wrangler d1 create wcrow`，在 Pages 项目里绑定 `DB`
2. 执行建表 SQL（`functions/api/works.js` 顶部注释里已给出）
3. 用一次性脚本把 `content/*.md` 导入 D1（可按现成的 works 字段映射）
4. 给写接口加鉴权（否则任何人都能改库），再在后台调用
5. 访问 `/api/works` 验证返回，前台会自动优先使用它
6. 删除 `content-index.json` 与 Actions（或保留双轨，前台优先级已定）

> 取舍：D1 换来即时发布与协作，但失去「内容即文件」的 Git 版本历史与零运维特性；
> 对**单人长期写作**的站点，Markdown + 自动索引已经是够用且更省心的方案。
